## Question

ระบบจะเลือกส่วนข้อความจากเอกสารและ Q&A ที่ดูแลเองมารวมเป็น context ให้ LLM อย่างไร, จะตอบเมื่อข้อมูลเพียงพอหรือปฏิเสธเมื่อไม่พออย่างไร, และลูกค้าหรือแอดมินควรเห็นชื่อเอกสารหรือหัวข้อที่ใช้ตอบหรือไม่?

## Comments

Resolution: รุ่นแรกใช้ semantic retrieval ด้วย sentence-transformers เดิม โดยค้นเฉพาะ Q&A และส่วนข้อความที่ Published, Ready และเป็นของธุรกิจเดียวกับช่องทางแชต ไม่ทำ reranking ด้วยโมเดลเพิ่ม เพื่อให้ติดตั้งและทำงานบน CPU ได้ง่าย

### การแบ่งและทำดัชนีเอกสาร

- ทำ Unicode normalization และปรับ line endings แต่รักษาหัวข้อ ย่อหน้า รายการ และข้อความตาราง Markdown ไว้
- แบ่งตามหัวข้อและย่อหน้าก่อน แล้วรวมเป็นส่วนละไม่เกิน 1,200 ตัวอักษร โดยซ้อนบริบทจากส่วนก่อนหน้าสูงสุด 200 ตัวอักษร ย่อหน้าที่ยาวเกินขนาดจึงค่อยตัดแบบแข็ง
- แต่ละส่วนเก็บลำดับ หัวข้อใกล้ที่สุด และ metadata ของเอกสาร ข้อความที่ใช้สร้าง embedding ประกอบด้วย title, product, version, heading และเนื้อหาส่วน เพื่อให้คำถามชื่อสินค้าค้นเจอสเปกที่เกี่ยวข้อง

### การเลือก context

- ฝังคำถามหนึ่งครั้ง แล้วค้น Q&A และส่วนข้อความแยกเป็นสองกลุ่มด้วย score threshold เดียวกัน ค่าเริ่มต้นยังเป็น `0.55` และปรับได้จาก config
- รับผู้สมัครสูงสุด 3 Q&A และ 6 ส่วนข้อความ ตัดส่วนข้อความซ้อนกันหรือซ้ำกัน แล้วเรียงตาม similarity รวมกัน บทบาทและลำดับความสำคัญเมื่อ Q&A ขัดกับเอกสารให้เป็นไปตามประเด็น “กำหนดบทบาท Q&A เดิมร่วมกับเอกสาร”
- ส่งให้ OpenRouter สูงสุด 6 แหล่งและรวมไม่เกิน 8,000 ตัวอักษร โดยเรียงจากเกี่ยวข้องมากไปน้อย พร้อม source ID และ metadata ส่งเฉพาะข้อมูลชุดนี้กับคำถามลูกค้า

### การตอบและปฏิเสธ

- ถ้าไม่มีผลลัพธ์ผ่าน threshold ให้ตอบข้อความ insufficient knowledge ที่ตั้งค่าไว้ทันทีโดยไม่เรียก OpenRouter
- หากมี context ให้ LLM ตอบจากข้อมูลที่ส่งให้เท่านั้น และคืนสถานะ `answer`, `needs_clarification` หรือ `insufficient_knowledge` พร้อมรายการ source IDs ที่ใช้อ้างอิง ระบบตรวจว่า source ID ทุกตัวอยู่ใน context ที่ส่งไป
- ถ้าคำถามขาดชื่อรุ่นหรือรายละเอียดที่จำเป็น ให้ถามกลับหนึ่งคำถามสั้น ๆ ด้วยสถานะ `needs_clarification` ถ้าข้อมูลยังไม่พอหรือขัดแย้งกันจนเลือกข้อเท็จจริงไม่ได้ ให้ปฏิเสธแทนการคาดเดา
- การเรียก embedding, Qdrant หรือ OpenRouter ล้มเหลวเป็น `service_error` เหมือนเดิม ไม่รายงานว่าเป็นความรู้ไม่เพียงพอ

### การแสดงแหล่งข้อมูล

- หน้าแชตและ widget แสดงเฉพาะแหล่งที่ LLM อ้างอิงใต้คำตอบ ได้แก่ title, heading และ product/version ที่มี ไม่แสดงชื่อไฟล์ ข้อความดิบ score หรือ ID ภายใน
- Backend API เพิ่ม `sources` เป็น array ในผลสำเร็จ โดยรายการว่างได้ เพื่อให้เว็บภายนอกเลือกวิธีแสดงผลโดยไม่ต้องค้นข้อมูลเพิ่ม
- หน้า preview ของแอดมินแสดงข้อความส่วนที่ค้นได้ ชื่อเอกสาร revision และ similarity score สำหรับตรวจคุณภาพ แต่ข้อมูลตรวจสอบเหล่านี้ไม่ออกสู่ช่องทางลูกค้า
